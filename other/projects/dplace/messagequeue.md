In d/place, we used RabbitMQ as a central piece of infrastructure to handle real-time tile updates asynchronously. When a user modifies a tile on the shared canvas, the WebSocket server doesn’t process the update directly. Instead, it publishes the request to a RabbitMQ queue. This design choice decouples user interaction from backend processing, allowing the server to remain lightweight and responsive even during high user activity. RabbitMQ acts as a buffer that absorbs bursts of traffic, enabling what’s called backpressure handling — where updates are queued and processed at the consumer's pace rather than overwhelming the server. On the other side, consumer workers pull messages from the queue, validate them (e.g., bounds check, rate limiting, color whitelisting), update the state in Redis/PostgreSQL, and then broadcast the final result via WebSockets to all connected clients. This architecture improves reliability, scalability, and maintainability. It also makes it easy to extend the system — for example, we can later add moderation or logging just by introducing new consumers without modifying the core interaction flow. Overall, RabbitMQ helped us design a system that is robust under load, modular, and future-proof.
